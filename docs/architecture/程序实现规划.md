# 《方寸牌社》程序实现规划

> 文档分类：架构设计。状态：持续维护。

## 1. 目标与边界

首发目标是一款完全离线的 Windows 单机游戏，包含统一大厅、角色、豆子、存档和多种牌类玩法。

已经确定的玩法：

- 经典三人叫地主斗地主，不含癞子
- 大众麻将
- 四川血战麻将
- 四人日式立直麻将

第一阶段只完成一个完整的斗地主纵向切片。麻将不会与斗地主同时开工，以免规则、AI、界面和产品系统一起膨胀。

程序设计遵守三个原则：

1. 规则不依赖 Godot，能够直接运行自动测试和批量 AI 对局。
2. 角色、背景、牌桌和语音都是可替换内容，不进入规则代码。
3. 所有随机过程可复现，每局都可以保存、回放和定位问题。

## 2. 技术选择

- 引擎：Godot 4 C#/.NET 版
- 语言：C#
- 首发平台：Windows x64
- 网络：无，所有内容本地运行
- 测试：标准 .NET 测试项目
- 存档：带版本号的 JSON；写入时保留上一份备份
- 回放：规则版本、随机种子、初始配置和全部已接受操作

不使用复杂的 ECS，也不在第一阶段引入数据库。棋牌是清晰的回合制状态机，普通 C# 领域对象和事件流更容易验证。

## 3. 总体分层

```text
Godot 表现层
  场景、动画、输入、音频、对话气泡、牌和角色显示
            │ 玩家意图 / 状态快照
            ▼
应用层
  对局控制器、AI 调度、存档、回放、豆子、角色选择
            │ 命令 / 事件
            ▼
纯 C# 规则层
  洗牌发牌、合法操作、牌型判断、回合状态、结算
            │
            ▼
内容与配置层
  角色定义、皮肤、背景主题、规则预设、台词、音频路径
```

### 3.1 规则层

规则层禁止引用 `Godot.Node`、图片、动画和音频。它只处理牌、玩家、阶段、操作与分数。

每次操作采用统一流程：

```text
Command（想做什么）
    → Validate（当前是否允许）
    → Event（实际发生了什么）
    → Reduce（更新 GameState）
    → Snapshot（提供给界面或 AI）
```

这样可以让提示、托管、AI、回放和界面共用同一套合法操作来源，不会出现“按钮允许出牌但规则引擎拒绝”的两套逻辑。

### 3.2 应用层

应用层负责一局游戏如何运行，但不决定牌型是否合法：

- 创建对局和注入随机种子
- 接收玩家输入并提交命令
- 请求 AI 决策
- 控制动画期间的输入锁
- 保存回放
- 对局结束后更新豆子、战绩和角色进度
- 将规则状态转换成适合界面消费的只读数据

AI 只获得该座位实际可见的 `PlayerObservation`，不直接读取其他玩家手牌。提示和托管通过相同的 AI 接口工作，但可以使用不同策略参数。

### 3.3 Godot 表现层

表现层只负责“怎么显示”：

- 背景和桌面主题
- 手牌布局与选择动画
- 角色头像、立绘、表情和气泡
- 按钮、弹窗、教程和音效
- 从规则事件生成出牌、碰杠、胡牌、炸弹等演出

规则状态先立即更新，表现层依次消费事件做动画。动画可以跳过或加速，但不会改变规则结果。

### 3.4 内容层

角色使用独立定义，不把角色写死在场景中。建议的数据结构：

```text
CharacterDefinition
  id
  display_name
  portrait / full_body
  expression_images
  voice_lines
  dialogue_set
  ai_personality_id
  preferred_table_theme
  source_note
```

背景和牌桌也使用 `ThemeDefinition` 管理。大厅或对局场景只引用内容 ID，因此以后替换原创角色、个人使用的二创角色或新背景时，不需要修改程序。

角色美术和 AI 牌风默认分离。同一个角色可以换皮肤而保持牌风，也可以在角色定义中改用另一套 AI 参数。

## 5. 画面与分辨率策略

建议以 `960×540` 作为逻辑设计画布，1920×1080 时正好 2 倍显示。相比 640×360，它更适合中文字体、20 张扑克牌和日麻密集信息，同时仍能保持明确的像素颗粒。

- 首发只为 16:9 做精确排版
- 非 16:9 分辨率使用安全区和留边，不拉伸牌面
- 像素贴图使用最近邻采样
- 背景可以使用较高分辨率整图，不强迫它与角色使用同一像素密度
- 手牌、按钮和关键文字单独制作，不能从概念图中裁切
- 概念图先作为布局和气氛参考，之后拆成背景、前景遮挡、桌面与交互层

场景建议统一为以下层级：

```text
Background → Environment → Table → Characters → Game Pieces → HUD → Modal → Transition
```

这样角色、桌子与背景都可以独立替换，也容易处理牌不被立绘遮挡的问题。

## 6. 斗地主纵向切片

### 6.1 规则状态机

```text
准备 → 洗牌/发牌 → 叫地主/抢地主 → 确定地主并取得底牌
    → 轮流出牌 → 一方出完 → 倍数与豆子结算 → 结果页
```

需要先冻结的细节包括首叫人轮转、无人叫地主后的处理、具体叫抢顺序和封顶倍数。这些全部写进 `DoudizhuRuleConfig`，不散落在界面代码中。

### 6.2 核心对象

- `Card`：花色与点数；大小王单独表示
- `Hand`：持有牌和稳定排序
- `CardPattern`：单张、对子、三张、顺子、连对、飞机、四带二、炸弹、王炸等
- `PatternDetector`：识别所选牌型
- `PatternComparer`：判断能否压过上家
- `MoveGenerator`：枚举当前全部合法出牌
- `DoudizhuState`：地主、当前座位、手牌、上次出牌、倍数和阶段
- `DoudizhuRuleEngine`：验证并执行命令
- `SettlementCalculator`：春天、反春、炸弹与最终豆子结算

出牌提示直接使用 `MoveGenerator` 的结果排序，第一版优先：

1. 少拆炸弹和王炸
2. 少拆完整顺子、连对和飞机
3. 优先减少手数
4. 能走完时优先直接走完

普通 AI 在此基础上增加记牌、剩余手数估计和农民协作。第一版不使用机器学习。

### 6.3 界面场景

首个可玩界面需要：

- 三个座位与剩余牌数
- 玩家最多 20 张手牌的重叠布局
- 叫地主、抢地主、不叫、不抢按钮
- 提示、不出、出牌、托管按钮
- 当前轮到谁、底分、倍数与豆子
- 上轮牌、地主标记、对话气泡
- 结算弹窗和再来一局

界面不自行计算可出牌。按钮状态、可选牌和提示结果全部由应用层提供。

## 7. 豆子、存档与成长

豆子只用于对局反馈：

- 本地档案有初始豆子
- 不同牌桌只有底分差异
- 输赢按规则结算，不出现充值入口
- 余额不足以进入最低场时显示“免费补给”
- 免费补给直接恢复到固定额度，无广告、次数和等待限制
- 豆子不购买关键角色，避免无限补给破坏解锁逻辑

存档至少包含：

- `schema_version`
- 豆子与统计数据
- 已解锁角色、角色好感或成就进度
- 当前选择的角色、背景和设置
- 教程完成状态

保存流程使用“写临时文件 → 验证 → 替换正式文件 → 保留备份”，降低程序退出时损坏存档的风险。

## 8. 随机数与回放

不直接依赖运行时默认随机数实现。项目内固定一种确定性随机算法，并在每局记录种子。

回放记录保持最小且可重放，只保存：

- 操作序号和操作者
- 已接受的命令
- 产生的规则事件

开发版可以重新执行回放。以后遇到“AI 出了非法牌”或“结算不对”，使用种子和操作序列复现；默认不增加逐步状态哈希、镜像状态或第二套校验链路。只有实际出现无法定位的数据损坏问题时，才基于明确故障模型增加针对性诊断字段。

## 9. 测试策略

### 斗地主规则测试

- 每一种合法和非法牌型的固定牌例
- 所有牌型之间的大小比较
- 顺子、连对和飞机的边界
- 炸弹、王炸、春天、反春和倍数
- 任意状态下生成的提示都必须是合法操作

### 性质与模拟测试

- 洗牌后必须恰好有 54 张且不重复
- 发牌和底牌数量始终正确
- 任何操作都不能产生或丢失牌
- 当前玩家始终能够选择合法动作
- 对局必须最终结束
- 批量运行 AI 对局，捕获死循环和非法状态

界面测试只验证显示和输入映射；规则正确性不能依赖手工点击测试。

## 10. 麻将阶段的实现方式

斗地主发布级纵向切片完成后，先建立麻将公共模型：

- 牌、牌墙、手牌、副露、牌河、座位与轮次
- 摸牌、弃牌、吃、碰、杠、胡的命令框架
- 可见牌统计、向听数和有效牌接口

三种麻将只共享稳定的基础结构，不强行共享结算：

- 大众麻将：规则配置与基础番型
- 四川麻将：换三张、定缺、血战、查花猪与查大叫
- 日麻：役、符番、振听、宝牌、立直、本场与复杂流局

尤其日麻的胡牌判定和结算保持独立测试集，避免大量条件判断污染大众麻将和川麻。

## 11. 开发里程碑

### M0：工程骨架

- 建立 Godot C# 项目与 .NET 测试项目
- 完成规则层与 Godot 层的引用边界
- 建立确定性随机数、日志和基本 CI 测试命令
- 用纯色块跑通大厅到牌桌的场景切换

完成标准：命令行测试可运行，Godot 可进入空牌桌。

### M1：无界面的斗地主规则

- 发牌、叫抢地主、全部牌型、合法性与结算
- 提示枚举器
- 大量固定牌例和随机模拟

完成标准：三个测试 AI 能在命令行连续完成大量对局，无非法状态和死循环。

### M2：可玩的斗地主牌桌

- 手牌交互、操作按钮、出牌动画、角色头像和气泡
- 普通 AI、提示和托管
- 结算和再来一局

完成标准：玩家可以从发牌一直玩到结算，退出重进不会影响存档。

### M3：产品外壳

- 大厅、模式选择、豆子、免费补给、角色选择
- 设置、战绩、教程和规则百科骨架
- 背景与角色内容包加载

完成标准：形成可独立试玩的单机斗地主版本。

### M4：大众麻将

- 麻将公共内核
- 向听、有效牌、吃碰杠胡、提示与托管
- 大众麻将规则和牌桌界面

### M5：四川麻将与日麻

- 先完成四川血战
- 再以独立算分测试集完成日麻东风战
- 半庄战在日麻东风战稳定后开放

## 12. 第一轮开工清单

1. 安装 Godot C#/.NET 版和匹配的 .NET SDK。
2. 创建解决方案、Godot 主工程、规则库和测试库。
3. 定义 `Card`、确定性随机数和斗地主阶段状态机。
4. 先写牌型固定测试，再实现牌型识别与比较。
5. 做一个纯色灰盒牌桌，验证 20 张手牌的鼠标选择和布局。
6. 打通“一次玩家操作 → 规则事件 → Godot 动画 → 下一回合”。

在 M1 完成前，不制作复杂角色动画、不接入麻将代码，也不把概念图切成正式素材。
